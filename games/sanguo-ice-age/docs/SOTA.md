## 3. 当前最大验收差距（按伤害排序，R3 改写）

### 差距一（新）：合同红灯与收口——离「能合并」只差工程纪律

双内核断层已收敛为一颗**探针合同红灯**：`bridge-project-view` 要求 `projectView` 把
`flags.gameOver` 字符串归一为布尔，实现透传字符串——功能正常、合同不符、`npm run probe`
退出码 1。加上工作树 7 文件未收口、`.pw-ui.mjs` 调试脚本在库外游走。这些是纪律问题不是
设计问题，但**任何一项不清，验收即不通过**（ACCEPTANCE §7 红线 1/2）。

### 差距二：克制教学的最后一公里（唯一没交付的 R2 硬性项）

三国 SLG 坐标系的核心主张「克制要能被学会」还差一步数据接线：systems 乘区（1.25/1.15，
单测钉死）→ `resolveBattle` result → 预览 bonusText / 战报乘区区块。UI 骨架、中文标签、
渲染逻辑全部就位，实测缺的只是 combat/actions 把数字吐出来（ACCEPTANCE P0-17 证据链）。

### 差距三：有败局无终局

失败幕地基已立（差距解除），但 60 天「春回」胜利结局两侧皆无（`flags.victory` 纯占位）——
玩家现在**只可能输、不可能赢**，一局没有「打完」的概念。失败幕容器可复用，成本主要在
结算画卷美术与 60 天判定钩子（ACCEPTANCE P0-14 / P2-06 / P2-07）。

### 差距四：手感余账

冻损撤工提示、羁绊临门提示、断供前预警、动效节拍盘点、`layout.css` 令牌收编——单项都小，
合在一起决定「像不像一个上过 QA 的作品」。不阻合并，阻「SOTA」。

## 4. 优先级建议（R3 修订）

1. **P0 清红灯**：view 归一 `gameOver` 布尔（连带删掉消费方的真值/布尔双轨兼容）→
   `bridge-project-view` 转 pass；工作树收口提交；`.pw-ui.mjs` 出库。（差距一，红线 1/2）
2. **P0 补克制数字**：`resolveBattle` result 加 `counters`（或顶层 `troopAdvantage/factionAdvantage`），
   `previewRaid` bonusText 带 ±%——UI 零改动即点亮。（差距二，红线 3）
3. **P0 走查取证**：用在途的 Playwright 脚本跑一遍 0-error 启动、失败幕重开、刷新续玩、
   导入导出、托盘领赏、温度色四档，留录屏。（红线 4/5/7）
4. **P1 裁决三合同**：火炉级数 / bench 10k 目标 / 民心「连续 2 天」——改文档或改实现，二选一写死。（红线 8）
5. **P1 补终局**：60 天春回结算（复用失败幕容器）；顺手接 S-04 两小项（文件名天数、坏档严格拒绝）。
6. **P2 手感余账**：缓冲 8、羁绊临门、断供预警、动效盘点、令牌收编、对比度审计。

> R2 的告诫兑现良好：失败幕与托盘都写成了「消费 systems 数据」的形态，没有在旧内核上糊临时逻辑，
> 拆迁成本为零。克制数字接线时延续同一纪律：**数值只从 combat 常量出，不在 UI 层复算。**
